## Nexus 混合 Agent 系统 —— 接手总纲（已核查修正版）

### 一、系统定位与设计初衷

Nexus 的设计目标是用最低成本搭建一个由多个专项 Agent 组成的混合系统：一个轻量主控（Hermes 理念的执行层）负责路由和记忆，复杂编排交给 LangGraph，代码生成/推理交给 Claude、Codex 等外部 API，大文件用 Cloudflare R2 存，结构化状态用 Supabase Postgres 存。这个设计思路本身是合理的分层架构，问题主要出在"用四个 Hugging Face 免费 Space 白嫖算力"这个前提假设上，以及部分文档在描述 Hermes CLI 能力时存在虚构内容。

### 二、当前可行性结论（这是接手者必须先确认的事）

在动手部署前，任何接手者都应该先做这三件事而不是直接照抄脚本：

第一，登录 Hugging Face 账号，实际尝试创建一个 Docker SDK 或 Gradio SDK 的新 Space，确认当前账号是否仍处在免费 CPU Basic 层，还是已经被要求升级到 PRO。这个政策在2026年内多次调整，文档里写的"0美元/月"不能直接当作事实使用，必须以账号面板的实时提示为准。

第二，如果确实需要4个 Docker Space 才能实现"主控+编排+两个推理专用节点"的架构，那么大概率需要至少一个 PRO 账号（月费约9美元起），"完全免费"的说法应当从任何交付文档里删除，改为"低成本"。

第三，重新评估是否真的需要"Hermes CLI 跑在 HF Space 里对外提供 HTTP 服务"这个设计。`HANDBOOK.md` 已经做出了正确判断：官方 Hermes Agent 是本地/服务器上的 TUI 交互工具，不是可以直接部署为 Web 服务的 HTTP 后端，因此 Nexus 系统里真正跑在 Space 里对外提供 `/run`、`/health` 等 HTTP 接口的，其实是一个**自建的 FastAPI + Gradio 应用**，"Hermes"只是这个自建主控的命名灵感或人格设定来源，不是把官方 hermes-agent 二进制直接跑成了 Web 服务。这一点是整套方案里最容易被误读、也最需要在交接时讲清楚的地方。

### 三、系统架构（去除虚构部分后的实际版本）

```mermaid
flowchart LR
    U[用户/外部请求] -->|POST /run| H[hermes 主控 Space<br/>FastAPI+Gradio, 自建]
    H -->|按关键词路由| W[Cloudflare Worker<br/>鉴权+转发+保活]
    W --> L[langgraph Space<br/>编排引擎]
    W --> C[claude-code Space<br/>调用 Anthropic API]
    W --> X[codex Space<br/>调用 OpenAI 兼容 API]
    L --> R2[(Cloudflare R2<br/>大文件/Checkpoint)]
    L --> SB[(Supabase Postgres<br/>状态/日志/记忆)]
    H --> SB
    H --> R2
```

四个组件、鉴权入口、存储分层、保活机制这些设计本身没有问题，保留自 `HANDBOOK.md`。真正需要提醒接手者的是：这套架构里所有下游 Space 之间的通信、鉴权、路由，都是团队自己用 FastAPI/Worker 写的业务代码，"Hermes"、"LangGraph"这些名字更多是设计理念上的借鉴和命名，而不是直接把对应开源项目原样部署——尤其是 Hermes，官方产品形态和这里的用法有本质区别，接手者不要按照 `humes.txt` 里的"神仙用法"命令去调试主控 Space，那些命令在这个架构里根本不存在、不生效。

### 六、给接手者的行动建议

如果接手者的目标只是学习这套分层架构的设计思路（主控路由、存储分离、保活机制、凭证外置这四个原则本身是通用且合理的工程实践），那么可以直接沿用 `HANDBOOK.md` 里的目录结构、API 契约、部署步骤，只需要把"完全免费"的表述改成"低成本，部分组件可能需要小额付费"，并在实际创建 Space 之前先确认账号当前的免费层权限。
