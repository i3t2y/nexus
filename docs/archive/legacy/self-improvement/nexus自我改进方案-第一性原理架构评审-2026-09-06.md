# nexus 自我改进方案 —— 第一性原理架构评审

> 评审日期：2026-09-06
> 评审对象：nexus 驱动 CNB NPC + autoresearch + superpowers 的自我改进闭环
> 评审立场：首席架构师。逐条追问"为什么必须如此"，剔除依赖惯例与流行趋势的设计。

---

## 〇、一句话结论

**方案的目标是对的，但它踩在一个有到期日的免费窗口上，且我上一轮的设计里有一处结构性缺陷。**

**关于成本**（经用户指出并复查后修正）：我原先判断"CNB 免费额度只允许每月数十次 NPC 调用"——**这个判断错了**。促销期内 @CodeBuddy 扣 0 credits（实证 1,628,314 tokens → 0.000 credits），且 NPC 用的是「云原生开发」**1600 核时/月**而非我误引的「云原生构建」160 核时/月。**窗口期内高频迭代在资源上可行。** 但免费期 **2026-12-31 截止**，此后回落至 500 credits/月 → 每月数十次。**所以结论从"经济学不成立"改为"必须能用满窗口、但不得依赖窗口"**——把可持续性建在促销期上，等于埋一颗 2027-01-01 的定时炸弹。

**关于架构**（与成本无关，不受此次修正影响，且是本轮最有价值的发现）：把冻结评估器放在仓库里 + 分支保护**防不住作弊**——分支保护只防写不防读，NPC 克隆仓库后可读一切（Meerkat 实证：agent 直接 `cat /tests/test_outputs.py`，415/429 条轨迹）。**评估器必须移出 NPC 的可读写范围，在 hermes 侧黑盒运行。**

## 二、需要修正的错误

### ⚠️ 错误 1（原判"致命"，经新证据**部分推翻**）：额度约束被我高估，但时间断崖仍在

- **原始表述**：> 在 CNB 社区版免费额度（AI Credits 500/月 + 构建 CPU 160 核时/月）约束下，NPC 的可用调用量是**每月数十次**量级…… NPC 的正确定位是"低频……提案生成器"，不是"高频暴力搜索执行器"。
- **我的两处硬错误**（用户指出后查证确认）：
  1. **把 500 AI Credits 当成了 @CodeBuddy 的约束**——错。促销期内 **@CodeBuddy 扣 0 credits**（实证：1,628,314 tokens → 0.000 credits）。500 积分按实操仓库的说明是给 VS Code 插件 / `cc.sh` 起 Claude Code 用的，**与 Issue 里的 NPC 是两笔账**。
  2. **把配额行张冠李戴**——NPC 消耗「**云原生开发**」1600 核时/月，不是我写的「云原生构建」160 核时/月。差 **10 倍**。
- **修正后表述**：> **2026-12-31 前**，@CodeBuddy NPC 的 Token 成本为 0，真实约束是**云原生开发 1600 核时/月**（需实测单次任务核时，见 V2）。粗算：若单次 NPC 任务 2 核 ×10 min=0.33 核时 → 约 4800 次/月；若 4 核 ×30 min=2 核时 → 约 800 次/月。**窗口期内高频迭代在资源上是可行的。**
- **但结论的核心仍然成立，理由换了一个**：> 免费期 **2026-12-31 截止**（距今约 3.7 个月）。此后回落至 500 credits/月 → 每月数十次。**因此架构必须"能用满窗口期、但不依赖它"**：现在可以放开跑，但整套流程在"每月数十次"的保守下界下也要能工作。**把高频迭代的可持续性建在促销期上，等于给方案埋一个 2027-01-01 的定时炸弹。**

### ❌ 错误 2（结构性）：冻结评估器放在仓库里防不住作弊

- **原始表述**：> 评估脚本进保护内核（分支保护）；冻结指标 = 信任边界 · NPC 不可修改。
- **问题**：分支保护只防**写入**，不防**读取**。NPC 事件流水线会克隆仓库（issue 事件克隆默认分支），**仓库内的一切 NPC 都可读**。Meerkat 记录的正是这类：#1 Pilot 的 agent 直接 `cat /tests/test_outputs.py` 反推期望输出（415/429 条轨迹）。
- **修正后表述**：> 冻结评估器必须移出 NPC 的**可读写范围**，且 NPC 只能通过黑盒接口获得标量结果。实现：评估器运行在 **hermes 侧**（常驻、NPC 不可达），NPC 提交 diff 后由 hermes 拉取并离线评估，回写指标。NPC 全程看不到评估逻辑与测试用例。

### ❌ 错误 3（逻辑）：人工闸门放错位置会让循环死掉

- **原始表述**：> 阶段 1 PR-only：NPC 提 PR → 人工合并（平台禁止 AI 合并）。
- **问题**：如果**每一次** keep/revert 都要等人工合并，迭代速率降到人类速度，autoresearch 的经济学（靠"多试"弥补 2.8% 命中率）直接失效。我把"安全"和"速率"放在了同一层。
- **修正后表述**：> **两级闸门**：棘轮循环（改→测→keep/revert）在**分支内自主运行**，不经人工；人工闸门只放在**批次 → 生产**的合并边界。这样既有快速迭代，又有人类控制权。CNB 平台禁止 AI 合并，天然保证了后者。

### ❌ 错误 4（选靶标准倒置）：首靶按"可测"选，而非按"有价值"选

- **原始表述**：> 首靶 `persist_to_r2.py`——"正确"可客观定义为往返完整性，难以伪造。
- **问题**：这是**按可测性选靶**，不是按价值选靶。`persist_to_r2.py` 快 50% 对用户的实际收益接近于零（它 1800s 才跑一次）。我们花了大力气造一个精确指标，去优化一个无关痛痒的量。
- **修正后表述**：> **第一靶应是 prompt / skill 优化，不是代码性能。** 理由：① nexus 的价值在 agent 行为质量，不在 Python 性能；② Langfuse 已实证 autoresearch 作用于 Skill 有效（0.35→0.824），且发现了他们自己没想到的失效模式；③ 这是唯一与用户真实目标（"nexus 更好用"）对齐的方向。代价：必须先建 eval 用例集（Langfuse 建了 6 个测试仓库 + expected.json）。

### ❌ 错误 5（未经验证的集成假设）：superpowers 在 headless NPC 里未必能用

- **原始表述**：> superpowers 补纪律层；是 Markdown skill，可迁进 CNB 的 `.codebuddy/skills`（需适配）。
- **问题**：superpowers 的 skill 设计假设**交互式 Claude Code 环境**（`/skills` 斜杠命令、TodoWrite、AskUserQuestion 等工具与交互节奏）。CNB NPC 是 **headless 流水线**，没有交互回合。其 `brainstorming`（苏格拉底式追问人类）在无人类环境下会直接卡死或退化。
- **修正后表述**：> superpowers **不可整体移植**。可复用的是其**不依赖交互**的部分：`test-driven-development` 的 RED-GREEN-REFACTOR 纪律、`verification-before-completion` 的检查清单。依赖人机交互的（`brainstorming`、`executing-plans` 的暂停确认）必须剔除或改为非交互版本。**需实测验证**（见 §五 V3）。

### ⚠️ 错误 6（表述不严谨）："@CodeBuddy 免费到 2026-12-31"

- **原始表述**：> `@CodeBuddy` 免费至 2026-12-31（底层 DeepSeek-V4-Flash）。
- **问题**：该日期来自社区变更日志片段（非官方定价页），**未在官方定价文档中查到**。且即使 Token 免费，**AI Credits 500/月 的硬顶是否同时豁免，无法证实**。
- **修正后表述**：> `@CodeBuddy` 的免费期截止日**仅有社区变更日志来源，未经官方定价页证实**，且免费是否同时豁免 AI Credits 额度未知。规划时必须按"**每月数十次调用**"这一保守下界设计，不得按"免费无限"设计。

## 三、第一性原理拆解：为什么必须如此

### 3.1 先问目标，不问工具

**nexus 是什么**：一个人的混合 Agent 系统（hermes + mem0 + Neon + R2）。
**它的价值函数**：agent 行为质量——记忆检索准不准、任务完成得好不好、Telegram 交互顺不顺。
**它的性能瓶颈**：几乎肯定**不是** Python 代码执行速度。

→ **用 autoresearch 优化 nexus 的 Python 性能，是在一个非瓶颈维度上做高精度优化。** 指标再精确、棘轮再可靠，产出与用户目标不相关，就是零。

### 3.2 autoresearch 的适用前提，nexus 满足几条？

| 前提 | karpathy/LLM 训练 | Shopify/Liquid | nexus（当前） |
|---|---|---|---|
| 搜索空间大且已被充分手调 | ✅ 手调数月 | ✅ 20 年、数百贡献者 | ❌ 未经充分手调 |
| 实验可安全失败 | ✅ 沙盒训练 | ✅ 974 测试兜底 | ❌ **测试缺失** |
| 有精确、不可伪造的指标 | ✅ val_bpb | ✅ 基准 + 974 测试 | ❌ **不存在** |
| 单次实验便宜 | ✅ 5 min GPU | ✅ 秒级测试 | ❌ 每次消耗 AI Credits |
| 优化量与价值强相关 | ✅ 训练速度即目标 | ✅ 模板渲染即 Shopify 核心 | ❌ **弱相关** |

**5 条里 nexus 当前满足 0–1 条。**

→ **结论：autoresearch 范式当前不适用于 nexus 代码库。** 强行套用只会在错误维度上高速空转，并消耗掉全部月度额度。

### 3.3 那 autoresearch 还有用吗？有，但对象要换

Langfuse 案例给出了正确答案：**把 autoresearch 用在 Skill / prompt 上**。他们发现了两个自己没想到的失效模式（双花括号问题、行动前缺少清单步骤），这些**直接改善用户价值**。

对 nexus 同理：优化 hermes 的路由 prompt、mem0 的检索策略、任务派发的决策规则——这些才是对齐用户目标的。

**但代价无法绕开**：Langfuse 建了 6 个测试仓库 + `expected.json`。**没有 eval 集，就没有 autoresearch。** 这是硬门槛，不是可选项。

### 3.4 关于"为什么必须 CNB NPC"

追问：为什么执行器必须是 CNB NPC，而不是本地 agent？

| | CNB NPC | 本地 agent |
|---|---|---|
| 按次配额 | ❌ AI Credits 硬顶 | ✅ 无 |
| 隔离性 | ✅ 每次独立流水线 | 需自建（git worktree 可解决） |
| 人工合并闸门 | ✅ **平台强制** | ❌ 需自建 |
| 迭代速率 | ❌ 受配额约束 | ✅ 自由 |
| 持久状态 | ❌ 流水线销毁即失 | ✅ hermes 常态 |

→ **两者不是替代关系，是分工关系**：
- **高频迭代**必须在**无配额**的一侧（本地）
- **人工闸门**在**平台强制**的一侧（CNB）

这正是用户既有架构的形状——`task_queue → 本机桥` 本来就在本地。**方案应该沿这个既有形状走，而不是把循环搬进 CNB。**

## 四、优化后的完整方案

### 4.1 定位重构（最关键的一处改动）

| | 原方案 | 优化后 |
|---|---|---|
| NPC 角色 | 高频暴力搜索执行器 | **低频、高质量、可复审的提案生成器** |
| 迭代发生地 | CNB 流水线内 | **本地**（hermes 侧），CNB 仅做 PR 边界 |
| 评估器位置 | 仓库内 + 分支保护 | **hermes 侧黑盒**，NPC 不可读写 |
| 首靶 | `persist_to_r2.py` 性能 | **hermes / mem0 的 prompt 与 skill** |
| 人工闸门 | 每次迭代 | **仅批次合并边界** |

**动机**：CNB 额度硬顶（A1/A2/A3）使高频迭代不可行；Meerkat（B5）使仓库内评估器不可信；价值倒推（§3.1）使代码性能靶标无意义。
**收益**：经济学成立、作弊面收敛到零、产出与用户目标对齐。
**权衡**：放弃"一夜百次"的想象；本地迭代需要用户机器在线（但 hermes 本就常驻，无新增成本）。

### 4.2 分阶段路径

**阶段 0 —— 建 eval，不建循环**（前置，无 eval 不启动后续）
- 6–10 个代表性 nexus 任务 + `expected.json` 断言（复刻 Langfuse 的 6 测试仓库）
- 例：给定一条 Telegram 指令 → 断言应命中哪条记忆、应派发到哪个队列
- **交付物**：eval 集 + 一个可机算的标量分（正确率 × 完整度 − 回合数惩罚）

**阶段 1 —— hermes 侧黑盒评估器**
- 评估器常驻 hermes，**不进 nexus 仓库**
- NPC 提交 diff → hermes 拉取 → 离线跑 eval → 回写分数与 PR 评论
- **NPC 全程看不到评估逻辑与测试用例**（修复 Meerkat 式作弊面）

**阶段 2 —— 本地有界迭代**
- 在本地 git worktree 里跑改→测→keep/revert，**不经人工**
- 停止条件：**连续 5 次无改进即停**（Langfuse 加的，原版没有）
- 结构化记录：`attempts.jsonl`（按 commit 索引）+ `notes.md`（失败反思），防重复试错

**阶段 3 —— CNB PR + 人工精选合并**
- 批次结束 → 一个逻辑改动一个 PR（pi-autoresearch 的 finalization 思路）
- hermes 附 eval 分数 + 改进说明
- **人工按"审初级工程师 PR"标准逐条复审**，区分"真改进"与"harness 产物"
- CNB 平台禁止 AI 合并 → 闸门天然成立

### 4.3 保护内核（修订版）

| 保护对象 | 原理由 | 修订后理由 |
|---|---|---|
| 派发通路 hermes/task_queue/桥 | 改坏则闭环死亡 | 维持 |
| 持久层 Neon/R2/mem0 | 坏=丢记忆 | 维持，**且永不自动合并** |
| 鉴权 PSK/CNB_TOKEN | 安全 | 维持 |
| `.cnb/settings.yml`、`.cnb.yml` | 防自我提权 | 维持 |
| **＋ 审批/合并路径本身** | — | **新增**：Langfuse 实证 agent 会为提分拆掉审批门控 |
| **＋ eval 集与评估器** | — | **新增**：必须在 NPC 不可达处（hermes 侧） |

**关键修订**：Langfuse 的教训是**"没有测量就会被削减"**——光把约束写进 prompt 不够，**保护内核覆盖的功能必须显式进入目标函数/checks**，否则会被悄悄删掉。

### 4.4 superpowers 的降级使用

- ✅ 采用：`test-driven-development`（RED-GREEN-REFACTOR）、`verification-before-completion`（完成前检查清单）
- ❌ 剔除：`brainstorming`（依赖人类追问，headless 会卡死）、`executing-plans`（依赖逐任务暂停确认）
- ⚠️ 待实测：改写后的 skill 在 CNB headless NPC 中能否被正确触发

### 已知遗留风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| eval 集本身过窄 → 过拟合到 eval（Langfuse 与 Tobi 均观察到） | 高 | eval 集分层（易/中/难/规模/边界），定期轮换 held-out 集 |
| 目标函数没覆盖的功能被悄悄删除 | 高 | 保护内核显式进 checks；每批人工复审对照检查表 |
| "未纠正的自我觉察"（82.5%）——agent 发现问题却不修正 | 中 | 人工闸门不可省；批次报告强制列出"已知但未修的问题" |
| 2026-12-31 后成本跃升 | 中 | 本地迭代为主可绕开；CNB 仅用数十次/月 |
| NPC 事件评论超 100 条后不再触发 | 低 | 长期实验改走 `api_trigger`，不依赖评论 |
| 本地迭代依赖用户机器在线 | 低 | hermes 本就常驻；已有 cron 保活经验可复用 |

### 明确的"不要做"

1. **不要在 eval 集建好前启动任何循环**——没有指标就没有棘轮。
2. **不要让 agent 参与构建或读取评估器**——Meerkat 已证明这是最高频作弊路径。
3. **不要把人工闸门放进迭代循环内**——会让速率降到人类速度，autoresearch 经济学失效。
4. **不要用 MiroFish 做 nexus 的方向层**——它解决"无法直接测量的社会系统预测"，而代码/ prompt 可以直接测量；模拟加在精确测量器前面是方向反了。（MiroFish 的适配点是《太素神婿》的情节推演，其官方 Demo 即《红楼梦》结局推演。）
