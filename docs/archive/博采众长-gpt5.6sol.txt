# **Nexus 混合 Agent 系统：完整接手与低成本部署基线**

> **文档性质**：零上下文接手文档  
> **成熟度**：架构基线；不是“已验证可运行”的声明  
> **适用对象**：开发者、运维人员、技术负责人或后续接手的 AI  
> **事实原则**：仓库实际代码和平台官方文档优先于本文；未验证内容不得当作事实

## **1. 项目定义**

Nexus 是一个采用“计算与持久化分离”的混合 Agent 系统：

- 主控服务负责接收请求、鉴权、路由、任务状态和用户界面。
- LangGraph 类服务负责多步骤工作流和状态机。
- 不同模型供应商通过独立适配器提供推理或代码生成能力。
- Supabase/PostgreSQL 保存结构化状态、日志和长期记忆。
- Cloudflare R2 或其他 S3 兼容对象存储保存大文件、产物和备份。
- Cloudflare Worker 或等价网关提供统一入口、鉴权和转发。

“hermes”“claude-code”“codex”等名称应视为**内部服务角色名**，除非仓库代码确实直接集成了对应官方产品。尤其不要假设某个 CLI 工具天然提供 Nexus 所需的 HTTP API。

## **2. 第一性原理与设计边界**

系统要解决的核心问题不是“堆叠多个 Agent”，而是：

1. 在计算节点可能重启、休眠或重建的情况下保存任务状态。
2. 让不同推理后端共享统一调用协议。
3. 防止密钥分散在代码和多个仓库中。
4. 让失败任务可以追踪、重试和恢复。
5. 在可控成本下逐步扩容，而不是一开始拆成过多服务。

因此应遵守以下原则：

- **状态外置**：计算节点不得把本地磁盘当作唯一持久存储。
- **接口稳定**：业务层调用内部统一接口，不直接绑定某个模型 ID。
- **默认最小部署**：原型阶段优先单服务模块化部署，确认负载后再拆分。
- **强制鉴权**：生产环境不得存在“未设置密钥就自动放行”的逻辑。
- **幂等与可恢复**：每个任务都必须有稳定的 `task_id`，关键写入可以重复执行。
- **事实可验证**：套餐、配额、端口、模型名称和 SDK 用法在部署当天查官方文档。

## **3. 推荐架构**

```mermaid
flowchart LR
    U[用户或上游系统] --> G[统一网关]
    G --> C[主控 API / Dashboard]
    C --> O[工作流编排器]
    C --> A1[推理适配器 A]
    C --> A2[推理适配器 B]

    C --> DB[(PostgreSQL / Supabase)]
    O --> DB
    A1 --> DB
    A2 --> DB

    C --> OS[(R2 / S3 对象存储)]
    O --> OS

    M[监控与告警] --> G
    M --> C
```

### **3.1 两种部署形态**

**起步形态：单服务模块化部署**

把主控、工作流和模型适配器部署在同一个 FastAPI 应用中，内部以 Python 模块调用。优点是成本低、网络故障面小、调试简单。

适合：

- 原型验证；
- 低并发；
- 单人或小团队；
- 尚未确认托管平台套餐与免费额度。

**扩展形态：多服务部署**

主控、编排器和模型适配器分别部署，通过网关调用。优点是故障隔离和独立扩容更好，但会增加冷启动、网络、鉴权和运维成本。

只有出现以下情况时才建议拆分：

- 某组件资源占用明显不同；
- 不同组件需要独立发布；
- 并发或安全域要求不同；
- 单服务已经成为可靠性瓶颈。

## **4. 服务职责**

| 服务 | 主要职责 | 不应承担的职责 |
|---|---|---|
| Gateway | 外部鉴权、速率限制、请求转发、请求 ID | 长时间运行的 Agent 逻辑 |
| Controller | 请求接收、路由、任务生命周期、Dashboard | 保存唯一数据副本 |
| Orchestrator | 多步骤工作流、暂停与恢复、检查点 | 管理平台密钥 |
| Model Adapter | 将统一请求转换为供应商 API 请求 | 决定系统级业务流程 |
| PostgreSQL | 状态、日志、记忆、幂等键、任务队列元数据 | 大型二进制产物 |
| Object Storage | 产物、备份、检查点大对象 | 高频结构化查询 |
| Monitor | 健康检查、指标、告警 | 通过规避平台规则强制保活 |

## **6. 统一 API 契约**

### **6.1 外部任务入口**

```http
POST /v1/tasks
Authorization: Bearer <token>
Idempotency-Key: <unique-key>
Content-Type: application/json
```

```json
{
  "prompt": "请分析这个代码库并给出重构计划",
  "capability": "workflow",
  "preferred_adapter": null,
  "metadata": {
    "user_id": "user-123"
  }
}
```

建议立即返回 `202 Accepted`：

```json
{
  "task_id": "task_01...",
  "status": "queued",
  "created_at": "2025-01-01T00:00:00Z"
}
```

长任务不应让一个 HTTP 请求持续等待数分钟。调用方通过以下接口查询：

```http
GET /v1/tasks/{task_id}
POST /v1/tasks/{task_id}/cancel
POST /v1/tasks/{task_id}/retry
```

### **6.2 内部执行接口**

```http
POST /internal/v1/execute
Authorization: Bearer <internal-token>
X-Request-ID: <request-id>
```

```json
{
  "task_id": "task_01...",
  "thread_id": "thread_01...",
  "input": {
    "prompt": "..."
  },
  "limits": {
    "timeout_seconds": 120,
    "max_output_tokens": 4000
  }
}
```

所有服务统一返回错误结构：

```json
{
  "error": {
    "code": "UPSTREAM_TIMEOUT",
    "message": "Model provider timed out",
    "retryable": true,
    "request_id": "req_01..."
  }
}
```

## **7. 路由策略**

不要仅依赖关键词路由。推荐按以下顺序决策：

1. 调用方明确指定能力；
2. 安全和权限规则；
3. 输入类型与上下文长度；
4. 成本、延迟和模型可用性；
5. 规则分类器；
6. 默认适配器。

路由结果应记录：

```json
{
  "selected_service": "orchestrator",
  "selected_adapter": "provider_a",
  "reason_code": "MULTI_STEP_WORKFLOW",
  "policy_version": "2025-01"
}
```

这比保存自由文本“思考过程”更适合审计，也不会暴露内部推理。

## **8. 数据模型**

建议至少包含以下表：

```sql
create table if not exists tasks (
    id text primary key,
    idempotency_key text unique,
    status text not null,
    capability text,
    selected_service text,
    selected_adapter text,
    input jsonb not null,
    output jsonb,
    error jsonb,
    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now()
);

create table if not exists task_events (
    id bigserial primary key,
    task_id text not null references tasks(id),
    event_type text not null,
    payload jsonb,
    created_at timestamptz not null default now()
);

create table if not exists checkpoints (
    id text primary key,
    task_id text not null references tasks(id),
    sequence_no integer not null,
    state jsonb,
    object_key text,
    created_at timestamptz not null default now(),
    unique(task_id, sequence_no)
);

create table if not exists memories (
    namespace text not null,
    memory_key text not null,
    value jsonb not null,
    expires_at timestamptz,
    updated_at timestamptz not null default now(),
    primary key(namespace, memory_key)
);

create table if not exists service_health (
    service_name text primary key,
    status text not null,
    details jsonb,
    checked_at timestamptz not null default now()
);
```

### **8.1 存储边界**

- 小型结构化状态：PostgreSQL。
- 大型文本、压缩包、模型产物和二进制文件：对象存储。
- 数据库只保存对象键、摘要、大小和内容类型。
- 不建议把临时预签名 URL 长期保存在数据库；保存对象键，需要时重新签名。
- 对象上传后计算 SHA-256，下载和恢复时校验。

## **9. 工作流检查点**

LangGraph 或其他状态机框架的数据库适配器、连接池和 prepared statement 行为可能存在兼容差异。不能笼统规定“必须使用某个端口”。

部署前应做最小验证：

1. 查数据库平台当前提供的 direct、session pooler 和 transaction pooler 连接方式；
2. 查实际驱动及检查点库是否依赖会话级 prepared statements；
3. 分别运行建表、写入、恢复和并发测试；
4. 只有通过测试的连接方式才能写入生产配置。

首次启动时执行一次幂等 `setup` 或 migration；应用实例不应各自在高并发启动时争抢建表。

## **10. 安全要求**

### **10.1 强制要求**

- 生产环境缺少 `NEXUS_API_KEY` 时启动失败，不得自动放行。
- 外部密钥与内部服务密钥分离。
- 数据库服务角色密钥只存在于可信后端。
- Secrets 只通过托管平台或密钥管理器注入。
- 日志默认清除 Authorization、Cookie、API key 和用户敏感信息。
- 对任务创建、文件上传、重试和取消实施权限检查。
- Worker 到私有后端的访问方式必须按托管平台官方规则验证。

### **10.2 不应采用的做法**

- 多账号规避配额；
- 模拟流量规避休眠或风控；
- 用随机抖动掩盖自动化行为；
- 把公开 `/health` 当作数据库保活写接口；
- 将服务角色密钥下发到浏览器；
- 把供应商名称硬编码成系统能力。

正常健康检查和合规的定时任务可以使用，但应遵守平台服务条款。

## **12. 可靠性设计**

任务状态建议采用明确状态机：

```text
queued
  → running
  → succeeded
  → failed_retryable
  → failed_terminal
  → cancelled
```

要求：

- 使用 `Idempotency-Key` 防止重复创建任务；
- 重试采用指数退避和随机抖动，但仅用于减轻拥塞，不用于规避检测；
- 只重试明确可重试的网络错误、限流和暂时性上游错误；
- 对写操作使用幂等键或事务；
- 设置最大尝试次数；
- 超过阈值进入死信状态；
- 每次状态变化写入 `task_events`；
- 熔断器应按供应商和模型分别统计。

## **13. 可观测性**

每个请求至少记录：

- `request_id`
- `task_id`
- 服务名与版本
- 路由决策代码
- 上游延迟
- 状态码
- 重试次数
- 输入/输出 token 数量（若供应商提供）
- 估算费用
- 错误代码

核心指标：

- 任务成功率；
- P50/P95/P99 延迟；
- 排队时长；
- 冷启动比例；
- 上游限流率；
- 单任务平均成本；
- 数据库连接池使用率；
- 对象存储失败率；
- 检查点恢复成功率。

## **14. 部署顺序**

### **阶段 A：本地验收**

1. 启动 PostgreSQL 或测试数据库；
2. 启动 S3 兼容测试存储；
3. 执行 migration；
4. 启动单体版 Nexus；
5. 使用模拟模型适配器完成闭环；
6. 运行单元、集成和契约测试；
7. 验证任务中断后可以恢复。

### **阶段 B：托管服务准备**

部署当天从官方页面核实：

- 计算平台是否允许所需 SDK 和容器；
- 套餐是否收费；
- 休眠、冷启动和磁盘持久性；
- 私有服务访问方式；
- 出站网络和端口；
- Worker 请求、CPU、Cron 和子请求限制；
- 对象存储容量与操作计费；
- 数据库容量、连接数、备份和暂停策略。

不能把论坛、聚合价格网站或旧截图作为唯一依据。

### **阶段 C：最小生产部署**

1. 创建数据库并执行 migration；
2. 创建私有对象存储桶和最小权限凭证；
3. 部署 Controller 单体版；
4. 配置网关、鉴权和速率限制；
5. 接入一个模型供应商；
6. 完成 smoke test；
7. 配置日志、指标、告警和备份；
8. 再决定是否拆分 Orchestrator 和其他 Adapter。

### **阶段 D：拆分部署**

只有单体版验收通过后才拆分：

1. 固化内部 API 契约；
2. 增加契约测试；
3. 为每个服务配置独立内部凭证；
4. 验证网关故障时的行为；
5. 验证冷启动和超时预算；
6. 逐个迁移，不一次性拆完。

## **15. 验收标准**

### **功能验收**

- 相同幂等键不会创建两个任务；
- 任务状态可查询；
- 路由可人工覆盖；
- 数据库和对象存储均正确写入；
- 服务重启后任务可恢复；
- 取消操作不会继续产生模型费用；
- 无效密钥返回 401；
- 无权限操作返回 403；
- 上游超时返回标准错误结构。

### **灾难恢复验收**

- 可从对象存储恢复最近一次备份；
- 可校验备份哈希；
- 可以在空数据库中重建核心表；
- 恢复步骤有自动化脚本；
- 明确 RPO 和 RTO；
- 至少定期进行一次恢复演练。

### **性能验收**

不要预先承诺“50 并发平均小于 2 秒”这类未经测量的指标。应先记录基线，再制定 SLO，例如：

- API 接单 P95 小于 500 ms；
- 不含模型推理的内部路由 P95 小于 200 ms；
- 任务成功率不低于 99%；
- 可重试错误最终恢复率不低于 95%。

模型端到端延迟应单独统计。

## **16. 成本模型**

固定成本和可变成本应分开计算：

```text
月成本 =
计算平台订阅或实例费用
+ 数据库存储与计算
+ 对象存储容量和操作费用
+ Worker 或网关费用
+ 模型输入费用
+ 模型输出费用
+ 监控与日志费用
```

对每个任务记录：

```text
estimated_cost =
input_tokens × input_unit_price
+ output_tokens × output_unit_price
+ storage_operations
+ execution_time_cost
```

“零成本”“固定 \$9/月”或“四个服务全部免费”都不能在未核实当前套餐时写成保证。正确表述应是：**架构支持低成本起步，实际费用由部署当天的平台政策和调用量决定。**

## **17. 旧方案必须删除或改写的内容**

以下内容若存在于附件，应从最终权威文档中删除：

- 未经 CLI `--help` 或官方文档验证的命令；
- 把交互式 CLI 直接描述成 HTTP 服务；
- 过时或未来模型名称；
- 与正文无关的论文和引用；
- 固定免费额度承诺；
- “多账号”“防检测”“规避风控”等策略；
- 由 PDF 提取乱码产生的伪代码；
- 无源码依据的“代码可直接运行”声明；
- 要求公开完整内部思维链的内容。

复杂决策应公开**可审计的步骤、假设、证据和结果**，而不是输出私密的逐字内部推理。
