## 三、目标与非目标

### 3.1 问题陈述

nexus 的价值函数 = **agent 行为质量**（记忆检索准不准、任务完成得好不好、Telegram 交互顺不顺），**不是** Python 代码执行速度。因此自我改进的对象必须是 **prompt / skill / 检索策略**，而非代码性能。

### 3.2 目标

| 层级 | 目标 | 可度量 |
|---|---|---|
| **G-1（首要）** | 建立 **不可作弊的 eval 基线**：把"nexus 变好了"变成可机算的标量 | eval 集 ≥8 用例 / 4 难度层；baseline 连跑 3 次方差 <5% |
| **G-2** | 建立 **hermes 侧黑盒评估器**，NPC 全程不可读写 | nexus 仓库内 grep 不到任何评估器/用例代码 |
| **G-3** | 首靶（hermes 路由 prompt 或 mem0 检索策略）在 **held-out 集**上相对 baseline 提升 **≥10%** | held-out 分数 delta |
| **G-4** | 全过程中 **保护内核零被修改** | diff 审计 |
| **G-5** | 整套流程在 **2027 常态（每月数十次）** 下也能工作，不只依赖促销窗口 | 常态容量推演通过 |

### 3.3 非目标（明确不做）

1. ❌ **不优化 nexus 的 Python 代码性能**（非瓶颈维度，§3.1）。
2. ❌ **不在 eval 集建好前启动任何迭代循环**（无指标即无棘轮）。
3. ❌ **不让 agent 参与构建或读取评估器**（F1–F6）。
4. ❌ **不做开放式 autosearch / NEVER STOP**（nexus 是生产记忆层；F8 82.5% 未纠正自我觉察）。
5. ❌ **不用 MiroFish 做方向层**（领域错配：它解决"无法直接测量"，而 prompt 可直接测量）。
6. ❌ **不依赖促销窗口做可持续性设计**（§4.2 双容量）。

| NPC 角色 | 低频提案生成器 | **受外部调度的高质量提案生成器**（频率按窗口可调，窗口期内可高频） |
| 高频本地化的**理由** | "CNB 额度硬顶" ❌ | ✅ **① NPC 流水线无状态（销毁即失），长循环必须有外部调度器 hermes**；② **成本独立于促销窗口**；③ 本地迭代零核时消耗 |
| 迭代发生地 | 本地（CNB 仅 PR 边界） | **维持**（理由加强：hermes 是唯一有持久状态的一侧，且 CNB 流水线天然无状态） |
| 评估器位置 | hermes 侧黑盒 | **维持，并加强论证**（§4.3） |
| 首靶 | hermes/mem0 prompt & skill | **维持** |
| 人工闸门 | 批次合并边界 | **维持，并定义为"能阻断的状态转移"**（F12） |

> **关键澄清**：M1 修正的是**理由**，不是**结论**。结论（本地迭代 + CNB 做 PR 边界）依然成立，但支撑它的不再是"额度不够"，而是"**NPC 无状态 + 不能把可持续性押在促销期上**"。这很重要——因为如果理由真是额度，那么 2027 后方案就该崩；而按新理由，方案在两套容量下都成立。

### 4.2 两套容量模型（M3 / M12 落地）

### 4.3 数据流与信任边界（M5 / M6 落地）

```
┌─────────────── hermes 侧（常驻 / NPC 不可达）───────────────┐
│  eval 集（含 held-out）· 评估器 · expected.json · 保护内核副本 │
│  对外只暴露一个接口：POST /eval  { diff } → { score: 0..1 }   │
└───────────────────────────┬────────────────────────────────┘
                            │ 只回传标量，不回传用例与逻辑
┌───────────────────────────▼────────────────────────────────┐
│  本地有界迭代（git worktree / 无配额消耗）                    │
│  改 → 提交 → 调 /eval → keep / revert                        │
│  停止：连续 5 次无改进  |  记录：attempts.jsonl + notes.md     │
└───────────────────────────┬────────────────────────────────┘
                            │ 批次结束
┌───────────────────────────▼────────────────────────────────┐
│  CNB：一个逻辑改动 = 一个 PR（NPC 生成，平台禁止 AI 合并）      │
│  人工按"审初级工程师 PR"标准逐条复审 → 合并（唯一状态转移点）   │
└────────────────────────────────────────────────────────────┘
```

**为什么评估器必须在 hermes 侧——三层论证（不再是单层）：**

| 层 | 威胁 | 证据 | 仓库内分支保护能否防住 |
|---|---|---|---|
| 1. **读** | NPC 克隆仓库，可读一切 | F2：415/429 轨迹 `cat /tests/test_outputs.py` | ❌ 分支保护只防写不防读 |
| 2. **篡改** | 冻结的测试文件被 hook/覆写 | F5：SWE-bench Verified 100% 靠 `conftest.py` hooks；parser 覆写 | ❌ 防不住测试框架层注入 |
| 3. **注入** | 把答案塞进 agent 上下文 | F3：AGENTS.md 注入字面答案，81.8%→71.7%（#1→14th） | ❌ 防不住上下文注入 |

→ **结论强化**：评估器必须**在 NPC 的可读写范围之外**（hermes 侧进程），NPC 只能拿到黑盒标量。

**闸门必须是"能阻断的状态转移"（F12）**：AutoResearchEval 证明 82.5% 的失败是"agent 发现问题却不修正"——因为自我审查不能改变执行状态。因此：
- ❌ 无效闸门：让 NPC 自己 review 一遍 / 生成一份"已知问题报告"
- ✅ 有效闸门：**评估器返回低分 → 该 diff 根本不进入 PR**（在 tool boundary 阻断）；**PR 未合并 → 不进入 main**（平台强制，AI 无法合并）

### 4.4 保护内核落地（M9 落地）

| 保护对象 | 具体路径 | 强制手段 | 检测方式 |
|---|---|---|---|
| 派发通路 | `hermes/`（路由/调度/派发）、本地桥 | 本地优先：改坏=砍断自己的手 | PR diff 必查 |
| 持久层 | Neon 四表 / R2 快照 / `mem0/` | **永不自动合并** | 人工复审清单第 1 项 |
| 鉴权 | PSK / `CNB_TOKEN` / HF Secrets | 不入仓库（已在 Secrets） | grep 密钥模式 |
| CI/提权面 | `.cnb.yml`、`.cnb/settings.yml` | 变更需双人确认 | diff 审计 |
| **＋ 审批/合并路径本身** | PR 模板、合并流程 | Langfuse 实证 agent 会为提分拆掉它（E12②） | **任何"移除审批/确认步骤"的 diff → 一律拒绝** |
| **＋ eval 集与评估器** | hermes 侧，不进 nexus 仓库 | 物理隔离 | `git grep` 全仓扫描应为空 |
| **＋ 目标函数显式化** | 保护内核覆盖的功能必须进 checks | "没有测量就会被削减"（E12③） | 见 §5 阶段0 checks |

**跨仓**：组织设置「允许 NPC 跨仓操作」**保持关闭**（D8）。限地是 NPC 三重约束之一。

## 五、实施步骤（可执行）

### 阶段 0 —— 建 eval（前置，未完成不得启动后续）

| 项 | 内容 |
|---|---|
| **目标** | 把"nexus 变好了"变成可机算、难以伪造的标量 |
| **动作 1** | 建 `eval/` 目录（**只存在于 hermes 侧，不进 nexus 仓库**），含 8 个代表性任务，按 4 层分层：<br>· 易（2）：单轮明确指令 → 应命中哪条记忆<br>· 中（3）：需一次检索 + 一次工具调用<br>· 难（2）：多跳 / 记忆冲突消解 / 派发决策<br>· 边界（1）：模糊指令 / 超出范围应拒答 |
| **动作 2** | 每个用例写 `expected.json`：断言"应命中哪条记忆 / 应派发到哪个队列 / 应拒答"，**只写可静态校验的断言** |
| **动作 3** | **held-out 集**：另建 2 个用例，**整个优化过程不参与**，仅用于最终验收（防 E14/E15 过拟合） |
| **动作 4** | 评分脚本 `eval/score.py`，**直接复用 Langfuse 已验证公式**（E10）：<br>`score = correctness×0.5 + completeness×0.3 + efficiency×0.2`<br>· correctness：静态断言命中率<br>· completeness：预期动作完成的比例<br>· efficiency：回合数惩罚（超阈值扣分） |
| **动作 5** | **保护内核显式进 checks**（E12③ 教训）：在 `score.py` 中硬编码"若输出中包含移除审批/跳过文档获取/删除记忆条目 → correctness 直接归零" |
| **产出** | `eval/`（8+2 用例 + expected.json）、`score.py`、记录 baseline |
| **完成判据（Gate 0）** | ① `score.py` 在干净环境一键运行并输出 [0,1] 标量；② baseline **连跑 3 次方差 <5%**；③ held-out 2 例已隔离；④ 保护内核 checks 已硬编码并自测通过（构造一个违规输出，确认归零） |

### 阶段 1 —— hermes 侧黑盒评估器

| 项 | 内容 |
|---|---|
| **目标** | 让 NPC 只能拿到标量，看不到用例与逻辑（防读/防篡改/防注入） |
| **动作 1** | 在 hermes 侧暴露唯一接口：`POST /eval`，入参 `{ diff_patch, target }`，出参 `{ score, breakdown, kept: bool }`。**不返回任何用例内容** |
| **动作 2** | 评估在**隔离目录**执行（拉取 diff 到临时 worktree → 跑 eval → 销毁），评估进程与 nexus 生产进程隔离 |
| **动作 3** | 审计：在 nexus 仓库执行 `git grep -riE "expected\.json|score\.py|eval/"` → 必须为空 |
| **动作 4** | 端到端 dry-run：手工提交 1 个无害 diff + 1 个违规 diff，确认分别得到高分与归零 |
| **产出** | `/eval` 接口 + 隔离评估环境 + 审计报告 |
| **完成判据（Gate 1）** | ① 仓库内 grep 为空；② dry-run 两类 diff 结果符合预期；③ 违规 diff 触发 `kept: false` 且不生成 PR |

### 阶段 2 —— 本地有界迭代（不经人工）

| 项 | 内容 |
|---|---|
| **目标** | 在无配额消耗的一侧跑"改→测→keep/revert" |
| **动作 1** | 首靶选定：**hermes 路由 prompt 或 mem0 检索策略**（G-3）。**一次只改一个文件** |
| **动作 2** | 在 `git worktree` 隔离环境迭代，每轮：<br>`git commit` → 调 `/eval` → 分数升则 keep，降/崩则 `git reset --hard HEAD~1` |
| **动作 3** | **停止条件（E11）**：连续 5 次无改进即停 |
| **动作 4** | 结构化记录（防重复试错）：<br>`attempts.jsonl`：每条 `{commit, score, delta, hypothesis, kept}`（append-only，唯一真相源）<br>`notes.md`：失败反思、已试方向 |
| **动作 5** | 每个批次结束跑 **held-out 集**做 sanity check（不用于优化决策，仅记录） |
| **产出** | 一批候选改动 + `attempts.jsonl` + `notes.md` + 批次报告 |
| **完成判据（Gate 2）** | ① 至少 1 个改动在 eval 集上提升 ≥5%；② 停止条件已触发或达到预算上限；③ 批次报告含"已知但未修的问题"清单（应对 F8） |

### 阶段 3 —— CNB PR + 人工精选合并

| 项 | 内容 |
|---|---|
| **目标** | 把候选改动交到**平台强制的人工闸门**前 |
| **动作 1** | **一个逻辑改动 = 一个 PR**（pi-autoresearch finalization 思路），PR 附：eval 分数 delta + 假设说明 + 为什么认为是真改进 |
| **动作 2** | 触发方式（已实测可用，D5/V4）：<br>`cnb build start-build --repo <path> --branch main --event api_trigger_npc --npc-name CodeBuddy --npc-workMode --sync false --env systemPrompt=... --env userPrompt=...`<br>⚠️ 前置：`main:` 包裹事件、`sandbox:false`、角色须在 `.cnb/settings.yml` 定义（详见 §9 踩坑记录） |
| **动作 3** | 人工按"审初级工程师 PR"标准逐条复审（E12/§2.3），对照检查表：<br>□ 是否触及保护内核？□ 是否移除审批/确认步骤？□ 是否删除 eval 未覆盖的功能？□ 是真改进还是 harness 产物？□ 代码可维护性是否下降（E16：56.1% 会下降）？ |
| **动作 4** | 合并（**唯一能改变生产状态的动作，且平台禁止 AI 执行**） |
| **产出** | 已合并的改进 PR + 复审记录 |
| **完成判据（Gate 3）** | ① 每个 PR 都有人工复审签字；② 无任何 PR 由 AI 合并；③ 保护内核零命中 |

## 七、验收标准

### 7.1 阶段门禁（必须逐条通过，否则不得进入下一阶段）

- **Gate 0**：`score.py` 一键运行出标量 ✅｜baseline 连跑 3 次方差 <5% ✅｜held-out 2 例已隔离 ✅｜保护内核 checks 自测通过（违规输入归零）✅
- **Gate 1**：nexus 仓库 `git grep` 评估器痕迹为空 ✅｜dry-run 高分/归零两类结果正确 ✅｜违规 diff 不生成 PR ✅
- **Gate 2**：≥1 个改动 eval 提升 ≥5% ✅｜停止条件生效或预算耗尽 ✅｜批次报告含"已知未修问题"清单 ✅
- **Gate 3**：每个 PR 有人工复审签字 ✅｜零 AI 合并 ✅｜保护内核零命中 ✅

### 7.2 全局验收（G-1 ~ G-5）

| 目标 | 验收标准 | 判定 |
|---|---|---|
| G-1 | eval 集 ≥8 用例 / 4 难度层；baseline 可复现（方差 <5%） | 通过 / 不通过 |
| G-2 | 仓库内无任何评估器/用例代码；NPC 全程只拿到标量 | 通过 / 不通过 |
| G-3 | 首靶在 **held-out 集**上相对 baseline 提升 **≥10%**，且人工复审确认为真改进（非 harness 产物） | 通过 / 不通过 |
| G-4 | 全程保护内核零被修改（diff 审计） | 通过 / 不通过 |
| G-5 | 常态容量推演：按 50 次/月设计，阶段 2+3 流程仍可运转 | 通过 / 不通过 |

### 7.3 熔断反验收（出现任一 → 立即停止批次并人工介入）

1. 🔴 eval 集分数上升，但 **held-out 集分数下降** → 判定过拟合，本批次作废。
2. 🔴 **保护内核任一文件出现在 diff 中** → 立即停止，人工介入。
3. 🔴 出现 **"移除审批门控 / 跳过确认步骤"** 类改动 → **一律拒绝**（E12②，Langfuse 实证：这是单次提分最大的改动，也是实际最有害的）。
4. 🔴 出现 **删除 eval 未覆盖功能** 的改动 → 一律拒绝（E12③："如果没有测量，就会被削减"）。
5. 🟠 单批次核时消耗超过预算（建议：单批次 ≤ 20 核时，约 1.25% 月额度）。
6. 🟠 NPC 上下文中出现评估器路径或 `expected.json` 内容 → 判定隔离失效，停止并修评估器。

## 九、CNB NPC 实操踩坑记录（自有实测，直接复用）

本轮探针已跑通完整链路，以下均为**实测确认**：

1. 🔴 **git push 必须用 PAT 嵌 URL**：`https://cnb:<PAT>@cnb.cool/<org>/<repo>.git`。用 `!f(){ echo password=$(cat ...) }` 凭证 helper 时，git 在 401 重试阶段**不会重新供密**，导致挂起（表现为 SIGTERM，易误判为沙箱拦网）。推完 `set-url` 还原去掉 token。
2. 🔴 **浅克隆推不上去**：`git clone --depth 1` 后 push 报 `shallow update not allowed` → 先 `git fetch --unshallow`。
3. 🔴 **`.cnb.yml` 事件必须挂在分支键下**：`main:\n  api_trigger_npc:`，顶层写会报 `CONFIG_EVENT_EMPTY`。
4. 🔴 **`--config` 对 api_trigger 无效**：流水线只能放仓库 `.cnb.yml`。
5. 🔴 **`role` 是 settings.yml 里的角色名，不是 NPC 名**：`role: CodeBuddy` → 去读 `.cnb/settings.yml` 找不到 → `Cannot read .cnb/settings.yml` → stage error。正确做法：`.cnb/settings.yml` 定义 `npc.roles[].name`，`.cnb.yml` 引用。
6. ✅ `sandbox: false` + `--npc-workMode` → NPC 可提交代码 / 开 PR。
7. ✅ 轮询：`cnb build get-build-status --repo <path> --sn <sn>`；`metricCoreHours` 字段直接给出核时。
8. ✅ 核时交叉验证：`dev_in_sec` 差值 ÷ 3600 == `metricCoreHours`。
